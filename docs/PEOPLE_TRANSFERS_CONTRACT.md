# People Transfers contract

This document defines the canonical PX9.1/PX9.2 cross-congregation People transfer boundary.

## Product semantics

A transfer is a controlled **copy into another authenticated tenant**. Claiming a transfer does not delete, archive or deactivate the source Person automatically. Destructive source cleanup remains an explicit local action after the receiving congregation confirms the result.

The transfer intentionally carries only data that remains meaningful across congregations:

- display name;
- preferred locale when present;
- ordinary profile phone/email/address when present.

It deliberately does **not** carry:

- emergency contacts;
- eligibility decisions or the source actors who made them;
- away/availability periods;
- labels;
- household/service-group membership;
- responsibilities/delegations;
- source-specific external IDs;
- archive state/reasons/history;
- assignment/recommendation/audit history.

These omitted facts are tenant-contextual, more sensitive, or require fresh authorization/configuration in the receiving congregation.

## Authority

### Send

`POST /api/people/transfers`

Required server-derived capabilities:

- `people.read`;
- `people.write`.

The browser may provide only a bounded unique list of opaque `personIds`. Tenant, actor, capabilities, source Person data, transfer identity, timestamps and token are server-owned.

### History

`GET /api/people/transfers`

Requires `people.read`. Returns outbound transfer metadata for the current tenant only. It never returns a claim code or transferred Contact values.

### Receive preview

`POST /api/people/transfers/preview`

Requires `people.read` + `people.write` and same-origin validation. The code is supplied in the request body, never a URL/query string. Preview is non-consuming and returns only display names, count and expiry.

### Claim

`POST /api/people/transfers/claim`

Requires `people.read` + `people.write` and same-origin validation. The claim is an atomic database operation. The receiving tenant is derived from the authenticated server session.

## Secret/token lifecycle

- The server generates at least 256 bits of cryptographically secure random entropy.
- The raw code is returned only in the successful send response and is never persisted.
- Persistence stores only a SHA-256 digest of the code.
- The raw code is never placed in logs, audit changed-field values, domain-event payloads, URLs, analytics, browser storage or service-worker caches.
- Transfers expire after 72 hours.
- A transfer can be claimed only once by a tenant.
- An ambiguous retry by the same destination tenant returns the already-claimed result rather than creating duplicate People.
- A claim attempt after another tenant has claimed, after cancellation or after expiry fails closed.
- Token comparison/lookup happens only in the service-role database boundary.

## Atomic receive

The claim transaction locks the transfer row, re-checks pending/expiry state, creates all destination Person entities, writes one audit/event pair for each created Person, records the complete destination result, and marks the transfer claimed before committing. Partial receive is not allowed.

Destination Person IDs are freshly generated by the database. Source Person IDs and source tenant IDs never become destination identities.

## Transfer status

Outbound history exposes one of:

- `pending`;
- `claimed`;
- `expired`;
- `cancelled`.

History may expose transfer ID, creation/expiry/claim/cancel timestamps, person count and source display names. It never exposes ordinary Contact values or the secret token.

## UI

The People Transfers tool must provide:

- Send and Receive modes;
- explicit privacy explanation before send;
- selected-person review and confirmation;
- one-time code presentation with expiry warning after send;
- outbound status/history without revealing old codes;
- receive-code input kept ephemeral in component memory;
- preview before claim;
- explicit claim confirmation;
- loading/empty/401/403/error/retry states;
- double-submit and stale-response ownership protection;
- pt-PT, en and es copy;
- no transfer code or transferred Contact PII in browser persistence.

## Audit/privacy boundary

Audit and domain events record resource/action identity only. They do not copy names, phones, emails, addresses or raw transfer codes. Receiver Person-create audit/event records identify the new Person aggregate without embedding transferred Contact values.
